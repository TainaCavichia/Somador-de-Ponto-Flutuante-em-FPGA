Parte 0 — Entendendo o projeto antes de tocar no computador

O que é esse "ponto flutuante simplificado" de 13 bits Um número nesse formato tem três partes, todas em uma única palavra de 13 bits:
CampoTamanhoSignificado
sign1 bit0 = positivo, 1 = negativo
exp4 bitsexpoente, sempre tratado como número sem sinal (0 a 15)
frac8 bitssignificando/fração, também sem sinal
O valor representado é: valor = (−1)sign × 0.frac × 2exp.
Exemplo: sign=0, exp="0101" (5), frac="10000000" → 0.10000000 (binário) = 0,5 em decimal → valor = 0,5 × 2⁵ = 16.
Regra de normalização Um número só é considerado "válido" (normalizado) se o bit mais significativo (MSB) do frac for '1'. Se o resultado de uma soma tiver esse bit em '0', o circuito precisa deslocar a fração para a esquerda até o MSB virar '1', diminuindo o expoente na mesma proporção. Se não sobrar expoente suficiente para isso, o número é pequeno demais e vira zero.
Os 4 estágios do circuito (isso é literalmente a estrutura do código VHDL)
  1. Sort (ordenar): compara os dois números de entrada e decide qual tem maior magnitude ("big", sufixo b) e qual é menor ("small", sufixo s).
  2. Align (alinhar): desloca a fração do número menor para a direita, para igualar os expoentes.
  3. Add/Sub (somar/subtrair): soma ou subtrai as frações já alinhadas (soma se os sinais forem iguais, subtrai se forem diferentes — é aritmética em sinal-magnitude).
  4. Normalize (normalizar): conta quantos zeros há à esquerda do resultado, desloca para a esquerda essa quantidade e ajusta o expoente. Trata também o caso de "carry-out" (estourou 1 bit na soma) e o caso "ficou pequeno demais, vira zero".
Essa é exatamente a razão de existirem os sinais fracb, fracs, fraca, sum e fracn no código: cada um representa o dado em um desses 4 estágios.
Por que o projeto pede para "validar antes de mexer" Se você já sair trocando os pinos e adaptando para a placa sem antes provar que o algoritmo matemático funciona, e algo der errado depois, você não vai saber se o erro está na lógica (matemática) ou na adaptação de hardware (pinos). Por isso a Etapa 1 existe: comprovar a matemática isolada, em simulação, sem depender da placa física.

Parte 1 — Instalar as ferramentas no seu computador

O que cada ferramenta faz
  • GHDL: um compilador/simulador de VHDL que roda por linha de comando. Ele não precisa de placa nenhuma — só "executa" seu código VHDL como se fosse um programa, gerando um arquivo de formas de onda.
  • GTKWave: o programa que abre esse arquivo de formas de onda e desenha os sinais graficamente ao longo do tempo, para você "ver" o circuito funcionando.
  • Intel Quartus Prime: o programa da Intel que converte seu VHDL em um arquivo que a FPGA física entende, e que também grava esse arquivo na placa.
  • Git/GitHub: onde você vai guardar e documentar o projeto (é a entrega final).

Parte 3 — Etapa 1: Simular o VHDL original (GHDL + GTKWave)

Objetivo desta etapa Comprovar que o algoritmo matemático (os 4 estágios) funciona, sem se preocupar ainda com a placa. Isso é 100% feito no terminal, sem abrir o Quartus.

3.1 — Criar o arquivo do somador

ABRIR um editor de texto (recomendo o VS Code — se não tiver, baixe em code.visualstudio.com, e dentro dele instale a extensão "WSL" para editar os arquivos do Ubuntu diretamente).

Crie o arquivo ~/somador-pf/rtl_original/fp_adder.vhd e cole exatamente este conteúdo (é o código do PDF, já limpo dos artefatos de formatação da extração do PDF — funcionalmente idêntico ao original): 
library ieee;
use ieee.std_logic_1164.all;
use ieee.numeric_std.all;

entity fp_adder is
    port(
        sign1, sign2 : in  std_logic;
        exp1, exp2   : in  std_logic_vector(3 downto 0);
        frac1, frac2 : in  std_logic_vector(7 downto 0);
        sign_out     : out std_logic;
        exp_out      : out std_logic_vector(3 downto 0);
        frac_out     : out std_logic_vector(7 downto 0)
    );
end fp_adder;

architecture arch of fp_adder is
    -- sufixos b, s, a, n = big, small, aligned, normalized
    signal signb, signs : std_logic;
    signal expb, exps, expn : unsigned(3 downto 0);
    signal fracb, fracs, fraca, fracn : unsigned(7 downto 0);
    signal sum_norm : unsigned(7 downto 0);
    signal exp_diff : unsigned(3 downto 0);
    signal sum : unsigned(8 downto 0);   -- 1 bit extra para o carry
    signal leado : unsigned(2 downto 0);
begin

    -- 1o estagio: ordenar (achar o maior numero)
    process(sign1, sign2, exp1, exp2, frac1, frac2)
    begin
        if (exp1 & frac1) > (exp2 & frac2) then
            signb <= sign1;  signs <= sign2;
            expb  <= unsigned(exp1);  exps <= unsigned(exp2);
            fracb <= unsigned(frac1); fracs <= unsigned(frac2);
        else
            signb <= sign2;  signs <= sign1;
            expb  <= unsigned(exp2);  exps <= unsigned(exp1);
            fracb <= unsigned(frac2); fracs <= unsigned(frac1);
        end if;
    end process;

    -- 2o estagio: alinhar o numero menor
    exp_diff <= expb - exps;
    with exp_diff select
        fraca <=
            fracs                        when "0000",
            '0' & fracs(7 downto 1)      when "0001",
            "00" & fracs(7 downto 2)     when "0010",
            "000" & fracs(7 downto 3)    when "0011",
            "0000" & fracs(7 downto 4)   when "0100",
            "00000" & fracs(7 downto 5)  when "0101",
            "000000" & fracs(7 downto 6) when "0110",
            "0000000" & fracs(7)         when "0111",
            "00000000"                   when others;

    -- 3o estagio: somar ou subtrair
    sum <= ('0' & fracb) + ('0' & fraca) when signb = signs else
           ('0' & fracb) - ('0' & fraca);

    -- 4o estagio: normalizar
    -- contar zeros a esquerda
    leado <= "000" when sum(7) = '1' else
             "001" when sum(6) = '1' else
             "010" when sum(5) = '1' else
             "011" when sum(4) = '1' else
             "100" when sum(3) = '1' else
             "101" when sum(2) = '1' else
             "110" when sum(1) = '1' else
             "111";

    -- deslocar a fracao de acordo com os zeros contados
    with leado select
        sum_norm <=
            sum(7 downto 0)             when "000",
            sum(6 downto 0) & '0'       when "001",
            sum(5 downto 0) & "00"      when "010",
            sum(4 downto 0) & "000"     when "011",
            sum(3 downto 0) & "0000"    when "100",
            sum(2 downto 0) & "00000"   when "101",
            sum(1 downto 0) & "000000"  when "110",
            sum(0) & "0000000"          when others;

    -- normalizar com condicoes especiais
    process(sum, sum_norm, expb, leado)
    begin
        if sum(8) = '1' then
            expn  <= expb + 1;
            fracn <= sum(8 downto 1);        -- houve carry-out: desloca p/ direita
        elsif (leado > expb) then
            expn  <= (others => '0');
            fracn <= (others => '0');        -- pequeno demais: vira zero
        else
            expn  <= expb - leado;
            fracn <= sum_norm;
        end if;
    end process;

    -- formar a saida
    sign_out <= signb;
    exp_out  <= std_logic_vector(expn);
    frac_out <= std_logic_vector(fracn);

end arch;
Atenção ao salvar Salve com o nome exato fp_adder.vhd (extensão .vhd, não .txt). No VS Code: Ctrl+S e confirme o nome no campo "Save As".

3.2 — Criar o testbench (o "programa de teste")

O que é um testbench É um segundo arquivo VHDL que não vira hardware de verdade — ele só existe para simulação. Ele "instancia" (chama) o seu fp_adder, aplica valores de entrada conhecidos, espera um tempo, e você confere na forma de onda se a saída bateu com o valor esperado calculado à mão.
Por que os 3 casos de teste abaixo Escolhi 3 casos que forçam o circuito a passar pelos 3 comportamentos especiais do 4º estágio (normalização) citados no enunciado do projeto — exatamente o que a professora pede para observar:
  1. Caso A força um carry-out na soma (resultado "estoura" 1 bit extra).
  2. Caso B força uma subtração com zeros à esquerda, testando o deslocamento e a contagem de zeros.
  3. Caso C força um resultado pequeno demais, que deve virar zero.
Fiz as contas à mão para cada um — veja a tabela logo abaixo do código.
Crie o arquivo ~/somador-pf/sim/fp_adder_tb.vhd: 
library ieee;
use ieee.std_logic_1164.all;

entity fp_adder_tb is
end fp_adder_tb;

architecture sim of fp_adder_tb is
    component fp_adder is
        port(
            sign1, sign2 : in  std_logic;
            exp1, exp2   : in  std_logic_vector(3 downto 0);
            frac1, frac2 : in  std_logic_vector(7 downto 0);
            sign_out     : out std_logic;
            exp_out      : out std_logic_vector(3 downto 0);
            frac_out     : out std_logic_vector(7 downto 0)
        );
    end component;

    signal sign1, sign2, sign_out : std_logic;
    signal exp1, exp2, exp_out : std_logic_vector(3 downto 0);
    signal frac1, frac2, frac_out : std_logic_vector(7 downto 0);
begin

    uut: fp_adder port map (
        sign1 => sign1, sign2 => sign2,
        exp1 => exp1, exp2 => exp2,
        frac1 => frac1, frac2 => frac2,
        sign_out => sign_out, exp_out => exp_out, frac_out => frac_out
    );

    process
    begin
        -- CASO A: forca carry-out
        sign1 <= '0'; exp1 <= "0110"; frac1 <= "11000000";
        sign2 <= '0'; exp2 <= "0110"; frac2 <= "10100000";
        wait for 20 ns;
        -- esperado: sign_out=0, exp_out="0111", frac_out="10110000"

        -- CASO B: subtracao com zeros a esquerda (testa deslocamento)
        sign1 <= '0'; exp1 <= "0101"; frac1 <= "10100000";
        sign2 <= '1'; exp2 <= "0101"; frac2 <= "10010000";
        wait for 20 ns;
        -- esperado: sign_out=0, exp_out="0010", frac_out="10000000"

        -- CASO C: resultado pequeno demais, vira zero
        sign1 <= '0'; exp1 <= "0001"; frac1 <= "10000000";
        sign2 <= '1'; exp2 <= "0001"; frac2 <= "10000000";
        wait for 20 ns;
        -- esperado: exp_out="0000", frac_out="00000000"

        wait;
    end process;

end sim;
Tabela de conferência (o que você deve ver no GTKWave)
Casosign1 exp1 frac1sign2 exp2 frac2sign_outexp_outfrac_outO que prova
A0 0110 110000000 0110 101000000011110110000carry-out: exp soma 1, frac desloca p/ direita
B0 0101 101000001 0101 1001000000010100000003 zeros à esquerda contados e deslocados corretamente
C0 0001 100000001 0001 10000000—000000000000cancelamento total → vira zero

3.3 — Compilar e simular com GHDL

DIGITAR no terminal, um comando de cada vez, dentro da pasta ~/somador-pf: 
cd ~/somador-pf

# 1) analisa (compila) o somador
ghdl -a --std=08 rtl_original/fp_adder.vhd

# 2) analisa o testbench
ghdl -a --std=08 sim/fp_adder_tb.vhd

# 3) elabora (monta) a unidade de teste
ghdl -e --std=08 fp_adder_tb

# 4) roda a simulacao e grava as formas de onda
ghdl -r --std=08 fp_adder_tb --wave=sim/onda.ghw

# 5) abre o visualizador
gtkwave sim/onda.ghw
Por que cada comando GHDL trabalha em 4 fases separadas, como um compilador de verdade: -a (analyze) verifica a sintaxe e "entende" o arquivo; -e (elaborate) monta a hierarquia (liga o testbench ao componente); -r (run) efetivamente simula e salva o resultado no arquivo .ghw; o GTKWave só serve para abrir esse arquivo e desenhar.
O que fazer dentro do GTKWave 1. Na coluna da esquerda (SST), clique em uut para expandir os sinais internos.
2. Selecione os sinais sign1, exp1, frac1, sign2, exp2, frac2, sign_out, exp_out, frac_out e clique em "Append" (ou arraste para o painel da direita).
3. Clique com botão direito em cada sinal → Data Format → Binary (ou Hexadecimal, para ficar mais fácil de ler).
4. Aperte a lupa "Zoom Fit" (ou Ctrl+Shift+F) para ver a linha do tempo inteira.
5. Compare os valores em cada trecho de 20 ns com a tabela acima.
Erros comuns nesta etapa
  • "entity fp_adder not found": você esqueceu de rodar o comando ghdl -a do fp_adder.vhd antes do testbench, ou está em uma pasta diferente. Rode os comandos na ordem, sempre a partir de ~/somador-pf.
  • gtkwave abre uma janela em branco: você esqueceu de arrastar os sinais para o painel — o programa não mostra nada por padrão até você adicionar sinais.
  • "command not found: ghdl": a instalação da Parte 1 não terminou certo — rode sudo apt install -y ghdl gtkwave de novo.

Parte 4 — Etapa 2: Adaptar o código para a placa DE10-Lite

O problema que você precisa resolver aqui O circuito fp_adder em si não muda nada — ele já é só lógica pura (sem pinos físicos). O que precisa de adaptação é o "circuito de teste" que conecta esse somador aos componentes físicos da placa (chaves, botões, displays). O livro (Listing 3.20 do PDF) fez isso para uma placa antiga com 8 chaves e 4 botões. A DE10-Lite tem 10 chaves (SW) e apenas 2 botões (KEY) — ou seja, você tem chaves sobrando e botões faltando, e precisa redistribuir os 26 bits de entrada (13+13) entre o que a placa realmente oferece.

4.2 — A decisão de projeto: como distribuir 26 bits em 10 chaves + 2 botões

Raciocínio (documente algo parecido com isso no seu relatório) Assim como o livro, vamos manter o operando 1 quase fixo (poucos bits variáveis, o resto é constante) e usar as chaves/botões livres para controlar o operando 2 por completo. A diferença da placa antiga para a DE10-Lite é que agora sobram chaves (10 em vez de 8) e faltam botões (2 em vvez de 4). Solução: usar 2 chaves extras no lugar dos 2 botões que faltam para compor o expoente do operando 2, fixando os 2 bits mais significativos desse expoente como constante — isso reduz a faixa de expoentes testáveis, mas ainda permite observar as diferenças de alinhamento (estágio 2) e todos os casos de normalização (estágio 4), que é o que a professora pede para demonstrar.
Mapeamento proposto
Sinal do fp_adderOrigem físicaObservação
sign1constante '0'igual ao livro
exp1constante "1000"igual ao livro
frac1'1' & SW(1) & SW(0) & "10101"só 2 bits variáveis, igual ao livro
sign2SW(9)era sw(7) no livro; adaptado para a chave mais alta da DE10-Lite
exp2"10" & KEY(1) & KEY(0)2 bits fixos + 2 bits dos botões (só 2 botões na DE10-Lite, versus 4 no livro)
frac2'1' & SW(8 downto 2)7 chaves, igual em quantidade ao livro (sw(6 downto 0))
Isso usa exatamente as 10 chaves (SW9 + SW8..SW2 + SW1 + SW0) e os 2 botões — nenhum pino sobra, nenhum falta.

4.3 — Saída: aproveitando que a DE10-Lite NÃO precisa de multiplexação

Uma simplificação importante em relação ao livro A placa do livro tinha só 4 dígitos de 7 segmentos compartilhando os mesmos pinos (por isso existiam os sinais an e o componente disp_mux — uma técnica chamada "multiplexação no tempo", que acende um dígito de cada vez, muito rápido, para enganar o olho). A DE10-Lite tem 6 displays de 7 segmentos (HEX0 a HEX5), cada um com seus próprios 8 pinos dedicados — ou seja, você não precisa do disp_mux nem do sinal an na adaptação para a DE10-Lite. Isso é uma simplificação real que vale a pena registrar no relatório como parte do "porquê" da adaptação.
Saída proposta
  • frac_out(3 downto 0) → decodificador de 7 segmentos → HEX0
  • frac_out(7 downto 4) → decodificador de 7 segmentos → HEX1
  • exp_out → decodificador de 7 segmentos → HEX2
  • sign_out → LEDR(9) (LED aceso = número negativo)

4.4 — Escrever o decodificador de 7 segmentos (hex_to_sseg)

Por que precisamos desse componente O PDF do livro cita um componente chamado hex_to_sseg, mas não mostra o código dele nesse trecho (provavelmente está em outro capítulo do livro, disponibilizado pela professora no Moodle). Ele converte um número de 4 bits (0 a F em hexadecimal) nos 7 sinais que acendem os segmentos do display. Antes de usar o código abaixo, procure no material do Moodle (o link da Etapa "Onde fazer?") se a professora já forneceu esse componente pronto — se sim, use o dela para manter consistência com o resto da turma. Se não encontrar, aqui vai uma implementação de referência válida para os displays da DE10-Lite (que são de catodo comum / segmentos ativos em nível baixo — ou seja, '0' aceso, '1' apagado):
Crie ~/somador-pf/rtl_de10lite/hex_to_sseg.vhd: 
library ieee;
use ieee.std_logic_1164.all;

entity hex_to_sseg is
    port(
        hex  : in  std_logic_vector(3 downto 0);
        sseg : out std_logic_vector(6 downto 0)  -- g f e d c b a (ativo em '0')
    );
end hex_to_sseg;

architecture arch of hex_to_sseg is
begin
    with hex select
        sseg <= "1000000" when "0000",  -- 0
                "1111001" when "0001",  -- 1
                "0100100" when "0010",  -- 2
                "0110000" when "0011",  -- 3
                "0011001" when "0100",  -- 4
                "0010010" when "0101",  -- 5
                "0000010" when "0110",  -- 6
                "1111000" when "0111",  -- 7
                "0000000" when "1000",  -- 8
                "0010000" when "1001",  -- 9
                "0001000" when "1010",  -- A
                "0000011" when "1011",  -- b
                "1000110" when "1100",  -- C
                "0100001" when "1101",  -- d
                "0000110" when "1110",  -- E
                "0001110" when others;  -- F
end arch;
Confirme a polaridade Antes de gravar na placa, abra o manual da DE10-Lite e confirme se os segmentos são mesmo ativos em '0'. Se ao gravar os displays mostrarem tudo apagado quando deveria estar aceso (ou vice-versa), inverta todos os bits do vetor sseg (troque cada '0' por '1' e vice-versa) — é o erro mais comum e mais rápido de corrigir nessa etapa.

4.5 — Escrever o "top level" (o arquivo que junta tudo e liga aos pinos)

Crie ~/somador-pf/rtl_de10lite/fp_adder_de10lite.vhd: 
library ieee;
use ieee.std_logic_1164.all;

entity fp_adder_de10lite is
    port(
        SW   : in  std_logic_vector(9 downto 0);
        KEY  : in  std_logic_vector(1 downto 0);
        LEDR : out std_logic_vector(9 downto 0);
        HEX0 : out std_logic_vector(6 downto 0);
        HEX1 : out std_logic_vector(6 downto 0);
        HEX2 : out std_logic_vector(6 downto 0)
    );
end fp_adder_de10lite;

architecture arch of fp_adder_de10lite is
    signal sign1, sign2, sign_out : std_logic;
    signal exp1, exp2, exp_out : std_logic_vector(3 downto 0);
    signal frac1, frac2, frac_out : std_logic_vector(7 downto 0);

    component fp_adder is
        port(
            sign1, sign2 : in  std_logic;
            exp1, exp2   : in  std_logic_vector(3 downto 0);
            frac1, frac2 : in  std_logic_vector(7 downto 0);
            sign_out     : out std_logic;
            exp_out      : out std_logic_vector(3 downto 0);
            frac_out     : out std_logic_vector(7 downto 0)
        );
    end component;

    component hex_to_sseg is
        port(
            hex  : in  std_logic_vector(3 downto 0);
            sseg : out std_logic_vector(6 downto 0)
        );
    end component;
begin
    -- mapeamento de entradas (ver secao 4.2 do tutorial)
    sign1 <= '0';
    exp1  <= "1000";
    frac1 <= '1' & SW(1) & SW(0) & "10101";

    sign2 <= SW(9);
    exp2  <= "10" & KEY(1) & KEY(0);
    frac2 <= '1' & SW(8 downto 2);

    fp_add_unit: fp_adder port map (
        sign1 => sign1, sign2 => sign2,
        exp1 => exp1, exp2 => exp2,
        frac1 => frac1, frac2 => frac2,
        sign_out => sign_out, exp_out => exp_out, frac_out => frac_out
    );

    hex0_unit: hex_to_sseg port map (hex => frac_out(3 downto 0), sseg => HEX0);
    hex1_unit: hex_to_sseg port map (hex => frac_out(7 downto 4), sseg => HEX1);
    hex2_unit: hex_to_sseg port map (hex => exp_out,               sseg => HEX2);

    LEDR(9) <= sign_out;
    LEDR(8 downto 0) <= (others => '0');

end arch;
Por que criamos um arquivo "top level" separado Assim o fp_adder.vhd original (o cérebro matemático) fica intocado — você só o reutiliza (component instantiation), sem editar sua lógica interna. Isso deixa claro, para quem for corrigir, que a "matemática" validada na Etapa 1 é exatamente a mesma sendo usada na placa física, só embrulhada em uma camada nova de conexões físicas.

4.6 — Refazer a simulação da versão adaptada

Repita o processo da seção 3.3, mas agora compilando os 3 arquivos (fp_adder, hex_to_sseg, fp_adder_de10lite) e um novo testbench que aplica valores em SW e KEY em vez de sign1/exp1/frac1 diretamente — isso comprova que o mapeamento de pinos da seção 4.2 não quebrou a lógica matemática (é literalmente o item 2 da "Ação" da Etapa 2 do enunciado). 
ghdl -a --std=08 rtl_original/fp_adder.vhd
ghdl -a --std=08 rtl_de10lite/hex_to_sseg.vhd
ghdl -a --std=08 rtl_de10lite/fp_adder_de10lite.vhd
ghdl -a --std=08 sim/fp_adder_de10lite_tb.vhd
ghdl -e --std=08 fp_adder_de10lite_tb
ghdl -r --std=08 fp_adder_de10lite_tb --wave=sim/onda_de10lite.ghw
gtkwave sim/onda_de10lite.ghw

Parte 5 — Etapa 3: Síntese física no Quartus e gravação na placa

O que muda aqui Até agora tudo era simulação (nenhum hardware real envolvido). A partir de agora você vai gerar o arquivo que a FPGA de fato entende (síntese) e gravá-lo fisicamente na placa via cabo USB.

5.1 — Criar o projeto no Quartus

ABRIR o Quartus Prime.
1. Menu File → New Project Wizard.
2. Clique Next. Em "Directory", escolha (ou crie) uma pasta, ex: ~/somador-pf/quartus. Em "Name", digite fp_adder_de10lite. Clique Next.
3. Em "Project Type", deixe "Empty Project" selecionado. Clique Next.
4. Em "Add Files", clique no botão "..." e adicione, um por um: fp_adder.vhd, hex_to_sseg.vhd, fp_adder_de10lite.vhd (das pastas rtl_original e rtl_de10lite). Clique Next.
5. Em "Family, Device & Board Settings": no campo Family, selecione "MAX 10 (DA/DF/DC/DE/DT/SA/SC/SE/ST)". No campo de busca de "Name filter" digite 10M50DA e selecione o dispositivo 10M50DAF484C7G (esse é o chip exato da placa DE10-Lite). Clique Next, depois Finish.
Confirme o part number O part number 10M50DAF484C7G é o padrão da DE10-Lite segundo a documentação da Terasic. Ainda assim, confira o adesivo/etiqueta física no próprio chip da sua placa (ou o manual da DE10-Lite) para ter certeza de que bate — usar o dispositivo errado impede a gravação.

5.2 — Definir a entidade top-level

No painel esquerdo ("Project Navigator"), aba "Files": clique com botão direito em fp_adder_de10lite.vhd → "Set as Top-Level Entity".
Por que isso é necessário Um projeto pode ter vários arquivos VHDL, mas o Quartus precisa saber qual deles representa "a placa inteira" — ou seja, qual entidade tem as portas que realmente vão virar pinos físicos. É a fp_adder_de10lite, não a fp_adder (que é só um componente interno).

5.3 — Atribuir os pinos (Pin Planner)

1. Menu Assignments → Pin Planner.
2. Na tabela que abre, cada linha é um dos sinais da sua entidade top-level (SW[0]...SW[9], KEY[0], KEY[1], LEDR[0]...LEDR[9], HEX0[0]...HEX2[6]).
3. Na coluna "Location" de cada linha, digite o nome do pino conforme a tabela da seção 4.1 (ex: para SW[0] digite PIN_C10) e aperte Enter.
4. Repita para todos os sinais. Para HEX1 e HEX2, procure a tabela completa no manual da DE10-Lite (mesma lógica de HEX0, seção 4.1) — o Quartus só vai deixar você compilar se todos os pinos usados estiverem atribuídos.
5. Feche o Pin Planner (ele salva automaticamente).
Como conferir se ficou certo Volte para a janela principal e abra Assignments → Pin Planner de novo — todas as linhas usadas devem ter uma "Location" preenchida, sem nenhuma em branco.

5.4 — Compilar

Menu Processing → Start Compilation (ou o ícone de "play" azul na barra de ferramentas). Isso pode demorar de 1 a 5 minutos.
O que esperar No final aparece uma janela "Compilation was successful", com um resumo mostrando quantos elementos lógicos (Logic Elements) foram usados. Alguns "Warnings" (avisos amarelos) são normais e não impedem a gravação; "Errors" (vermelhos) impedem — leia a mensagem, ela geralmente aponta o arquivo e a linha exata do problema.

5.5 — Gravar na placa

1. Conecte a placa DE10-Lite ao computador via cabo USB (o cabo USB Blaster, geralmente USB Mini-B).
2. Ligue a placa (chave de energia na lateral).
3. No Quartus, menu Tools → Programmer.
4. Clique em "Hardware Setup...", selecione "USB-Blaster" na lista, feche.
5. Clique em "Auto Detect" se a lista de dispositivos estiver vazia — deve aparecer o chip 10M50DA.
6. Marque a caixinha "Program/Configure" ao lado do arquivo .sof listado.
7. Clique em "Start".
Como saber que gravou A barra de progresso chega a 100% e aparece "Configuration Succeeded" (ou similar). A partir daí, mexer nas chaves SW e nos botões KEY da placa física já deve mudar os displays HEX na hora — sem precisar do computador.

5.6 — Testar os casos críticos na placa

Reproduza fisicamente, com as chaves e botões, os 3 casos da tabela da seção 3.2 (adaptando os valores de frac2/sign2/exp2 para os bits de SW/KEY conforme o mapeamento da seção 4.2) e confira se o HEX0/HEX1/HEX2 mostram os valores esperados de frac_out/exp_out, e se o LEDR(9) acende corretamente para os casos negativos.
Erros comuns nesta etapa
  • "Can't Access JTAG chain": cabo USB mal conectado ou placa desligada — confira o cabo e a chave de energia.
  • Displays mostram tudo apagado/tudo aceso: problema de polaridade do hex_to_sseg (veja o aviso da seção 4.4).
  • Erro "pin location conflicts" ao compilar: dois sinais diferentes com o mesmo "Location" no Pin Planner — revise a tabela, cada pino só pode aparecer uma vez.
